# תוכנית קבצים להגשה — ממ"ן 12

מסמך זה מפרט **בדיוק אילו קבצים צריך להכין**, ומה צריכים לכלול כל אחד מהם, כדי לייצר את
שני מסמכי ההגשה (אפיון וניתוח + עיצוב הפתרון) בפורמט PDF ו-DOCX, עם דיאגרמות Mermaid
השמורות כקבצי Markdown נפרדים.

מבנה תיקיות מוצע:

```
מסמכים/
  הגשה/
    אפיון-וניתוח/       ← קבצי המקור של מסמך האפיון (טיוטות לפי נושא)
    עיצוב-פתרון/         ← קבצי המקור של מסמך העיצוב (טיוטות לפי נושא)
    diagrams/            ← כל דיאגרמת Mermaid, קובץ נפרד לכל דיאגרמה
    output/               ← הפלט הסופי: PDF + DOCX
```

כל קובץ טיוטה (בתיקיות `אפיון-וניתוח/` ו-`עיצוב-פתרון/`) הוא פרק אחד. בסוף השבוע כל
הפרקים של מסמך אחד מתאחדים לקובץ Markdown אחד, שממנו מפיקים DOCX ואז PDF (ראו את
הפייפליין בתחתית מסמך "מסלול ההגשה").

---

## חלק א׳ — מסמך אפיון וניתוח (40% מהציון)

מסמך ללקוח שאינו מבין בתכנות. **אסור** שיכיל מונחים כמו מחלקה, API, בסיס נתונים, ירושה.

### `01-כללי-וייעוד.md`
- **כללי**: מהי המערכת במשפט-שניים, מי הלקוח (רשת מסעדות / מסעדה בודדת), ומה הבעיה
  שהמערכת פותרת עבורו (זרימת הזמנות ידנית, בזבוז מלאי, חוסר נראות בין המטבח למלצרים).
- **ייעוד המערכת**: המטרה הכללית — ניהול קצה-לקצה של הזמנה, מטבח, מלאי וניהול תפריט,
  עם מודול AI שמייעץ למטבח. למי מיועדת (בעלי מסעדות, צוות הסל).

### `02-דרישות-מערכת.md`
דרישות בשפה חופשית, **לפי מודול עסקי**, כולל דרישות שהלקוח לא ניסח במפורש אבל מתחייבות
מהמערכת (למשל: לא ניתן לאשר הכנת מנה שאין לה מלאי מספיק — דרישה מובלעת, לא רק "לנהל מלאי"):
- ניהול הזמנות (פתיחת שולחן, הוספת/עריכת/ביטול פריטים, סגירת חשבון)
- ניהול מטבח (תור הכנה בזמן אמת, מעקב סטטוס לכל מנה)
- מלאי ולוגיסטיקה (ניכוי אוטומטי, התרעות מלאי נמוך, דחיית מנה כשאין מספיק מלאי)
- שף חכם מבוסס AI (הצעת מתכונים ממלאי קיים, ייעוץ וסיוע לטבח)
- ניהול (תפריט, משתמשים והרשאות)

### `03-משתמשי-מערכת.md`
לכל אחד מ-4 סוגי המשתמשים: תיאור התפקיד + **רשימה מלאה** של כל פעולה שהוא יכול לבצע:
- מנהל (Admin) — תפריט, משתמשים, דוחות, מלאי
- מלצר (Waiter) — פתיחת שולחנות, יצירת/עריכת הזמנות
- טבח (Cook) — צפייה בהזמנות נכנסות, עדכון סטטוס הכנה, דחיית פריט
- מחסנאי (Warehouse Manager) — צפייה/עדכון מלאי, קבלת התרעות

### `04-use-case.md`
דיאגרמת Use-Case אחת לכל תפקיד/אזור פונקציונלי (בסגנון הדוגמה ב-Scutr — actor מחוץ
למסגרת המערכת, עיגול לכל פעולה, יחסי `<<include>>`/`<<extend>>` היכן שרלוונטי), ומתחת
לכל דיאגרמה — רשימה ממוספרת שמסבירה כל פעולה במשפט:
1. מלצר — ניהול שולחנות והזמנות
2. טבח — לוח המטבח (כולל דחיית פריט מסיבת מלאי)
3. מחסנאי — ניהול מלאי והתרעות
4. מנהל — ניהול תפריט ומשתמשים
5. שף חכם — הצעת מתכון, אישור לתפריט, שיחת ייעוץ

### `05-תהליכים-עיקריים.md`
תיאור מילולי + דיאגרמת Activity לכל אחד מהתהליכים העסקיים המרכזיים:
- מסלול הזמנה מלא: פתיחת שולחן → הוספת פריטים → קליטה במטבח → ניכוי מלאי בזמן אמת →
  הגשה → סגירת חשבון
- דחיית פריט במטבח כשאין מספיק מלאי, כולל ההודעה שחוזרת למלצר
- התרעת מלאי נמוך למחסנאי
- הצעת מתכון מה-AI על סמך מלאי קיים ואישורה כמנה חדשה בתפריט
- שיחת ייעוץ עם השף החכם ועדכון מתכון קיים

### `06-מדריך-למשתמש.md`
מדריך מלווה-מסכים — **צילום מסך אמיתי** לכל פעולה (לא תיאור בלבד), לפי תפקיד, בסדר:
התחברות → מלצר → טבח → מחסנאי → מנהל → שף חכם. כל צילום מלווה בהסבר קצר של הפעולה.

## חלק ב׳ — מסמך עיצוב הפתרון (60% מהציון)

מסמך טכני. חייב **שלא** להיות תלוי במימוש ספציפי (סוג בסיס נתונים, Web מול Win Form) —
תיאור הפתרון עצמו, גמיש לשינויים.

### `01-מבנה-מערכת.md`
ארכיטקטורה כללית ברמה גבוהה: Frontend (React+TS) / Backend (FastAPI) / בסיס נתונים
(PostgreSQL) / תקשורת בזמן אמת (WebSocket). דיאגרמת רכיבים אחת שממחישה את הזרימה בין
השכבות.

### `02-הנחות-עבודה.md`
הנחות עבודה מפורשות: משתמש אחד = תפקיד אחד קבוע, session מבוסס cookie, כל בקשה
עוברת דרך שכבת הרשאות אחידה, בסיס הנתונים הוא מקור האמת היחיד (Single Source of Truth).

### `03-מוסכמות-כתיבה.md`
מוסכמות שמות (Backend: PascalCase למחלקות, snake_case לפונקציות/משתנים; Frontend:
PascalCase לרכיבי React, camelCase לפונקציות; שמות קבצים תואמים את מה שהם מכילים) +
מוסכמות קוד (async לכל אורך ה-Backend, הפרדת שכבות API/Service/Model, הזרקת תלויות
במקום singletons גלובליים).

### `04-בסיס-נתונים.md`
טבלת שדות לכל ישות (User, Category, Dish, Ingredient, RecipeIngredient,
RestaurantTable, Order, OrderItem, StockMovement, AIRecipeSuggestion, AIChatSession,
AIChatMessage) — שם שדה, טיפוס, שימוש. בסוף — דיאגרמת ER מלאה.

### `05-ארכיטקטורת-שכבות.md`
תיאור השכבות ותפקיד כל אחת: `api/` (בקרים דקים) → `services/` (לוגיקה עסקית) →
`data_models/` (ORM בלבד) בצד השרת; `pages/` → `components/` → `services/` (קריאות
API) בצד הלקוח. הסבר קצר על מנגנון הזרקת התלויות (Container) שמחבר ביניהן.

### `06-מחלקות-וממשקים.md`
דיאגרמת Class לכל מודול מרכזי (הזמנות, מטבח, מלאי, תפריט, משתמשים, AI). לכל מחלקה:
היררכיית ירושה (אם קיימת), שדות ומתודות עיקריים, קשרים עם מחלקות אחרות.

### `07-דפוסי-עיצוב.md`
כל דפוס עיצוב (Design Pattern) בנפרד — הסבר כללי + **היכן בדיוק** הוא ממומש בפתרון:
- **Dependency Injection** — קונטיינר מרכזי שמזריק תצורה, לוגר וכל שירות
- **Repository** — הפרדת גישה לנתונים מהלוגיקה העסקית
- **Strategy** — בחירת התנהגות לפי תפקיד משתמש / סוג תנועת מלאי
- **State** — מחזור חיי הסטטוס של הזמנה ופריט הזמנה
- **Observer / Pub-Sub** — שידור עדכונים בזמן אמת למסכי מלצר/טבח/מחסנאי
- **Factory** — בניית בקשות/הנחיות עבור מודול ה-AI

### `08-שינויים-עתידיים.md`
שינויים עתידיים אפשריים ואופן ההטמעה שלהם בפתרון הקיים בלי לשבור אותו: הוספת סוג
משתמש חדש, ערוץ התרעה נוסף (למשל דוא"ל/SMS), ספק AI חלופי, מעבר לבסיס נתונים אחר.

### `09-דיאגרמות-רצף.md`
דיאגרמת Sequence לכל אחד מהתהליכים הקריטיים: איסוף פריט עם ניכוי מלאי אטומי, דחיית
פריט מסיבת מלאי, שידור עדכון בזמן אמת, קריאה למודול ה-AI ליצירת הצעת מתכון.
