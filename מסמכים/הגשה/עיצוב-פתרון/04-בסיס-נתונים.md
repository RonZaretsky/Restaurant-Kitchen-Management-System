# 4. מודל הנתונים

פרק זה מציג את מודל הנתונים של המערכת: את העקרונות אשר קבעו את צורתו, את השדות של כל
אחת מן הישויות, ואת כללי השלמות שהמבנה עצמו אוכף.

## 4.1 עקרונות המודל

בטרם נציג את הטבלאות, נפרט ארבע החלטות אשר חוזרות על עצמן בכל הישויות ומסבירות מדוע
המודל נראה כפי שהוא:

1. **אין מחיקה.** אף ישות אינה נמחקת. משתמשים, מרכיבים ושולחנות מושבתים בשדה בוליאני או
   במצב, פריטי הזמנה עוברים למצב סופי ונשארים גלויים, ותנועות מלאי אינן ניתנות לשינוי
   כלל. מכאן שכל מפתח זר במודל מצביע על רשומה אשר תמשיך להתקיים תמיד, ולא קיים מצב של
   רשומה מיותמת.

2. **מצב שניתן לחישוב אינו נשמר.** התרעת מלאי נמוך איננה ישות, כי מרכיב נמצא בחוסר כאשר
   הכמות שלו קטנה מן הרף שלו. באופן דומה, מצב "אושרה" של הצעת מתכון איננו שדה, מכיוון
   שהצעה נחשבת מאושרת כאשר קיימת מנה המצביעה עליה. שדה שמור עלול להתפצל מן המציאות
   בעוד שערך מחושב אינו יכול להתפצל ממנה, ומעבר לכך לא קיימת רשומת התרעה שניתן לשכפל,
   לשכוח לסגור או להשאיר פתוחה לאחר שהחוסר נפתר.

   הערה: לעיקרון זה קיים חריג אחד ומודע, והוא מצב ההזמנה בשלביה הפעילים. מצב זה נגזר
   ממצבי הפריטים שבהזמנה, אולם הוא כן נשמר בשדה ואיננו מחושב בכל קריאה. הסיבה מעשית: לוח
   המטבח ומסכי המלצרים מסננים לפי מצב זה, וסינון על ערך המחושב מאוסף הפריטים בכל שאילתה
   היה מייקר כל קריאה כדי לחסוך כתיבה אחת. המחיר של החריג מוכר לנו, ולפיכך המצב מחושב
   מחדש ונכתב בכל שינוי במצב פריט, תחת נעילת שורת ההזמנה. הפירוט נמצא בסעיף 7.6.

3. **ערך שהתקבל בהחלטה נשמר ואינו נקרא מחדש.** מחיר המנה נשמר בשורת פריט ההזמנה ברגע
   ההוספה, והחשבון מחושב תמיד מן המחירים השמורים ולעולם לא ממחיר המנה הנוכחי. אלמלא כן,
   שינוי מחיר בתפריט היה משנה למפרע חשבונות פתוחים.

4. **שדות כספיים וכמותיים הם עשרוניים מדויקים ולא נקודה צפה.** כמות מרכיב נשמרת בשלוש
   ספרות אחרי הנקודה וסכומים נשמרים בשתיים. חישוב בנקודה צפה צובר שגיאות עיגול, וביומן
   מלאי האמור להסביר את הכמות הנוכחית מדובר בתקלה המצטברת בשקט.

## 4.2 טבלאות הישויות

בטבלאות שלהלן, העמודה "מפתח" מציינת את תפקיד השדה במבנה, והעמודה "חובה" מציינת אם הוא
יכול להישאר ריק.

|---|---|---|---|---|

### 4.2.5 שורת מתכון

הקשר בין מנה למרכיב, יחד עם הכמות. זוהי ישות מקשרת בעלת מפתח ראשי מורכב משני הצדדים.

| שדה | טיפוס | מפתח | חובה | שימוש |
|---|---|---|---|---|
| dish_id | מספר שלם | ראשי + זר למנה | כן | המנה |
| ingredient_id | מספר שלם | ראשי + זר למרכיב | כן | המרכיב |
| quantity | עשרוני (10,3) | | כן | הכמות הדרושה למנה אחת |
| unit | ערך מתוך רשימה | | כן | חייבת להיות זהה ליחידת המרכיב |

הערה: המפתח המורכב אינו משמש כמזהה בלבד אלא גם ככלל, מפני שהוא מונע מאותו מרכיב להופיע
פעמיים באותו מתכון מבלי שנדרש כלל נפרד אשר יאכוף זאת בקוד. זוהי דוגמה לאכיפה שהמבנה
מספק בחינם.

הוא עדיין עשוי להשתנות.

### 4.2.8 פריט הזמנה

שורה אחת בהזמנה, כלומר מנה בכמות מסוימת. זוהי הישות המחזיקה את מרב המצב במערכת.

| שדה | טיפוס | מפתח | חובה | שימוש |
|---|---|---|---|---|
| id | מספר שלם | ראשי | כן | מזהה פנימי |
| order_id | מספר שלם | זר להזמנה | כן | ההזמנה שאליה שייך |
| dish_id | מספר שלם | זר למנה | כן | המנה שהוזמנה |
| quantity | מספר שלם | | כן | הכמות. חסומה ב-99 |
| status | ערך מתוך רשימה | | כן | ממתין, בהכנה, מוכן, בוטל, נדחה |
| notes | טקסט חופשי | | לא | הערת המלצר, למשל "בלי בצל" |
| cook_id | מספר שלם | זר למשתמש | לא | הטבח שלקח להכנה. תיעוד בלבד, אינו נעילה |
| price_at_add | עשרוני (8,2) | | כן | מחיר המנה ברגע ההוספה |

הערה: הכמות חסומה ב-99 מכיוון שסכום ההזמנה הוא סכום של מכפלות מחיר בכמות, והשדה
המחזיק אותו מוגבל בגודלו. תקרה על הכמות מבטיחה שהסכום לא יחרוג לעולם ממה שהשדה יכול
להכיל. מדובר אפוא בהגבלה הנובעת מן המבנה ולא מהעדפה עסקית.

### 4.2.9 תנועת מלאי

רשומה אחת ביומן המסביר את הכמות של מרכיב. זוהי הטבלה היחידה שהיא בלתי הפיכה לחלוטין.

| שדה | טיפוס | מפתח | חובה | שימוש |
|---|---|---|---|---|
| id | מספר שלם | ראשי | כן | מזהה פנימי |
| ingredient_id | מספר שלם | זר למרכיב | כן | המרכיב שהושפע |
| movement_type | ערך מתוך רשימה | | כן | קנייה, צריכה, פחת, התאמת ספירה |
| quantity_change | עשרוני (10,3) | | כן | הדלתא החתומה, חיובית או שלילית |
| reference_id | מספר שלם | | לא | ההזמנה שגרמה לצריכה. ריק בתנועה ידנית |
| performed_by | מספר שלם | זר למשתמש | כן | מי ביצע |
| timestamp | חותמת זמן | | כן | מתי |
| notes | טקסט חופשי | | לא | הערה חופשית |

הערה: תנועה מסוג "צריכה" נוצרת באופן אוטומטי בלבד, בעת לקיחת פריט להכנה, ואיננה ניתנת
לרישום ידני, שאם לא כן אותה מנה הייתה עלולה להיות מנוכה פעמיים. הכלל נאכף בשכבת האימות
של הבקשה, עוד לפני שהיא מגיעה ללוגיקה.
>
השדה `quantity_change` נשמר חתום ולא כגודל עם כיוון נפרד. בזכות זאת, הכמות ההתחלתית של
המרכיב ועוד סכום כל תנועותיו אמורים לתת בדיוק את כמותו הנוכחית, וזוהי בדיקת שפיות שניתן
להריץ בכל רגע. הכמות הנקבעת ביצירת המרכיב איננה תנועה, כמפורט בהנחה ה-9.

הערה: השדה `reference_id` אינו מפתח זר, וזאת במכוון. הוא מציין את ההזמנה שגרמה לצריכה,
אך אינו מוצהר כהפניה מבנית, מפני שתנועה ידנית מותירה אותו ריק וכך אותו שדה אינו נושא שני
מובנים מבניים שונים באותה עמודה. משמעות הדבר היא שזהו השדה היחיד במודל אשר המבנה אינו
מבטיח לגביו כי הוא מצביע על רשומה קיימת, והאחריות עליו מוטלת על שכבת הלוגיקה הכותבת
אותו.

### 4.2.10 הצעת מתכון

תוצר של פנייה לשירות הבינה המלאכותית. אין מדובר במנה, ולא ניתן להזמין אותה.

| שדה | טיפוס | מפתח | חובה | שימוש |
|---|---|---|---|---|
| id | מספר שלם | ראשי | כן | מזהה פנימי |
| requested_by | מספר שלם | זר למשתמש | כן | הטבח שביקש |
| prompt_used | טקסט חופשי | | כן | הפנייה המלאה שנשלחה, כולל הכיוון שהטבח הוסיף |
| generated_recipe | מסמך מובנה | | כן | ההצעה: שם, מרכיבים, אופן הגשה |
| ingredients_snapshot | מסמך מובנה | | כן | צילום המלאי ברגע הבקשה |
| created_at | חותמת זמן | | כן | מועד ההפקה |
| dismissed | בוליאני | | כן | נדחתה על ידי מנהל |

צילום המלאי נשמר מכיוון שבלעדיו לא ניתן להסביר בדיעבד מדוע הוצעה דווקא ההצעה הזו,
שהרי המלאי השתנה מאז. מדובר בתיעוד של הקלט ולא במטמון.

הערה: אין בישות זו שדה המציין כי ההצעה אושרה. הצעה נחשבת מאושרת כאשר קיימת מנה המצביעה
עליה, ותו לא. השדה `dismissed` הוא היחיד הנשמר, מפני שדחייה איננה מותירה שום עקבה אחרת
שניתן לחשב ממנה.

### 4.2.11 שיחת ייעוץ

הקשר לדיאלוג בין טבח לשירות הבינה המלאכותית, סביב נושא אחד.

| שדה | טיפוס | מפתח | חובה | שימוש |
|---|---|---|---|---|
| id | מספר שלם | ראשי | כן | מזהה פנימי |
| user_id | מספר שלם | זר למשתמש | כן | הטבח שפתח |

הערה: בדיוק אחד משני שדות הנושא חייב להיות מלא. ברמת המבנה שניהם שדות רשות, והכלל
נאכף בשכבת האימות. זוהי החלטה מודעת, מכיוון שמדובר בכלל עסקי ולא מבני, ואכיפתו בשכבה
המסבירה למשתמש מדוע הבקשה נדחתה עדיפה על פני כשל מבני המגיע כתקלה כללית.

### 4.2.12 הודעה בשיחה

הודעה בודדת בשיחת ייעוץ, של הטבח או של השירות.

| שדה | טיפוס | מפתח | חובה | שימוש |
|---|---|---|---|---|
| id | מספר שלם | ראשי | כן | מזהה פנימי |
| session_id | מספר שלם | זר לשיחה | כן | השיחה שאליה שייכת |
| role | ערך מתוך רשימה | | כן | הטבח או השירות |
| content | טקסט חופשי | | כן | תוכן ההודעה |
| created_at | חותמת זמן | | כן | מועד השליחה |

הערה: שתי ההודעות של סבב אחד נשמרות יחד או שאינן נשמרות כלל. אם הפנייה לשירות נכשלה,
גם השאלה איננה נשמרת, כדי שלא תיוותר בהיסטוריה שאלה תלויה שאיש לא ענה עליה.

## 4.4 כללי שלמות שהמבנה אוכף בעצמו

הטבלה שלהלן מסכמת אילו כללים עסקיים מוגנים על ידי המבנה עצמו, מבלי להסתמך על קוד אשר
יזכור לבדוק אותם. ההבדל בין השניים מהותי, מכיוון שכלל הנאכף במבנה אינו יכול להישבר בשל
נתיב קוד חדש שמישהו הוסיף ושכח לבדוק בו.

| הכלל העסקי | מה אוכף אותו |
|---|---|
| אין שני משתמשים בעלי אותו שם כניסה | אינדקס ייחודי, ללא הבחנת רישיות |
| אין שני מרכיבים בעלי אותו שם | אינדקס ייחודי, ללא הבחנת רישיות |
| אין שני שולחנות בעלי אותו מספר | אילוץ ייחודיות |
| אין שתי קטגוריות בעלות אותו שם | אילוץ ייחודיות |
| מרכיב אינו מופיע פעמיים באותו מתכון | מפתח ראשי מורכב |
| הצעה אינה מאושרת פעמיים | אילוץ ייחודיות על ההפניה מהמנה להצעה |
| כל הפניה מצביעה על רשומה קיימת (למעט `reference_id`, ראו 4.2.9) | מפתחות זרים, יחד עם הכלל שאין מחיקה |
| כמות ומחיר אינם מאבדים דיוק | טיפוס עשרוני מדויק, לא נקודה צפה |

כל שאר הכללים נאכפים בשכבת הלוגיקה העסקית, מכיוון שהם דורשים הקשר שהמבנה אינו מכיר:
כמה מלאי נחוץ לפריט מסוים, האם התפקיד מורשה, והאם המעבר בין המצבים חוקי. חלוקת עבודה זו
מכוונת, ולפיה המבנה שומר על מה שנכון תמיד ואילו הלוגיקה שומרת על מה שתלוי במצב.
