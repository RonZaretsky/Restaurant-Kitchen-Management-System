# 4. מודל הנתונים

## 4.1 עקרונות המודל

לפני הטבלאות, ארבע החלטות שחוזרות על עצמן בכל הישויות ומסבירות למה המודל נראה כפי שהוא.

**1. אין מחיקה.** אף ישות אינה נמחקת. משתמשים, מרכיבים ושולחנות מושבתים בשדה בוליאני או
במצב, פריטי הזמנה עוברים למצב סופי ונשארים גלויים, ותנועות מלאי אינן ניתנות לשינוי כלל.
מכאן שכל מפתח זר במודל מצביע על רשומה שתמיד תמשיך להתקיים, ואין מצב של רשומה מיותמת.

**2. מצב שניתן לחישוב אינו נשמר.** התרעת מלאי נמוך אינה ישות: מרכיב נמצא בחוסר כאשר
הכמות שלו קטנה מהרף שלו. מצב "אושרה" של הצעת מתכון אינו שדה: הצעה אושרה כאשר קיימת מנה
שמצביעה עליה. מצב ההזמנה בשלביה הפעילים נגזר ממצבי הפריטים שבה.

הנימוק: **שדה שמור יכול להתפצל מהמציאות, שדה מחושב לא יכול.** נוסף על כך, אין רשומת התרעה
שאפשר לשכפל, לשכוח לסגור או להשאיר פתוחה אחרי שהחוסר נפתר.

**3. ערך שהתקבל בהחלטה נשמר, ואינו נקרא מחדש.** מחיר המנה נשמר בשורת פריט ההזמנה ברגע
ההוספה. חשבון מחושב תמיד מהמחירים השמורים ולעולם לא ממחיר המנה הנוכחי. אחרת שינוי מחיר
בתפריט היה משנה למפרע חשבונות פתוחים.

**4. שדות כספיים וכמותיים הם עשרוניים מדויקים, לא נקודה צפה.** כמות מרכיב נשמרת בשלוש
ספרות אחרי הנקודה, וסכומים בשתיים. חישוב בנקודה צפה צובר שגיאות עיגול, וביומן מלאי שאמור
להסביר את הכמות הנוכחית זו תקלה שמצטברת בשקט.

## 4.2 טבלאות הישויות

בכל טבלה: **מפתח** מציין את תפקיד השדה במבנה, ו**חובה** מציין אם הוא יכול להישאר ריק.

### 4.2.1 משתמש

חשבון של עובד. הישות המרכזית ביותר בקשרים: היא מופיעה בחמישה מקומות אחרים כמבצע הפעולה.

| שדה | טיפוס | מפתח | חובה | שימוש |
|---|---|---|---|---|
| id | מספר שלם | ראשי | כן | מזהה פנימי |
| username | מחרוזת (50) | ייחודי | כן | שם הכניסה. הייחודיות אינה מבחינה בין אותיות גדולות לקטנות |
| password_hash | מחרוזת (255) | | כן | גיבוב הסיסמה. **לעולם אינו מוחזר בשום תשובה** |
| full_name | מחרוזת (100) | | כן | שם לתצוגה |
| role | ערך מתוך רשימה | | כן | מנהל, מלצר, טבח או מחסנאי |
| is_active | בוליאני | | כן | השבתה במקום מחיקה. מושבת אינו יכול להיכנס |
| created_at | חותמת זמן | | כן | מועד היצירה |

### 4.2.2 קטגוריית תפריט

קיבוץ של מנות. ישות קטנה בכוונה: היא רק שם.

| שדה | טיפוס | מפתח | חובה | שימוש |
|---|---|---|---|---|
| id | מספר שלם | ראשי | כן | מזהה פנימי |
| name | מחרוזת (50) | ייחודי | כן | שם הקטגוריה |

### 4.2.3 מנה

פריט בתפריט. מה שהמלצר מזמין והטבח מכין.

| שדה | טיפוס | מפתח | חובה | שימוש |
|---|---|---|---|---|
| id | מספר שלם | ראשי | כן | מזהה פנימי |
| name | מחרוזת (100) | | כן | שם המנה |
| description | טקסט חופשי | | לא | תיאור לתצוגה |
| price | עשרוני (8,2) | | כן | המחיר הנוכחי בתפריט |
| category_id | מספר שלם | זר לקטגוריה | כן | שיוך לקטגוריה |
| is_available | בוליאני | | כן | **נוצרת תמיד כלא זמינה.** אינה יכולה להפוך לזמינה בלי מתכון |
| prep_time_minutes | מספר שלם | | לא | זמן הכנה משוער |
| image_url | מחרוזת (255) | | לא | תמונה לתצוגה |
| created_at | חותמת זמן | | כן | מועד היצירה |
| source_suggestion_id | מספר שלם | זר להצעה, **ייחודי** | לא | ההצעה שממנה נוצרה, אם נוצרה מהצעה |

> **הייחודיות של `source_suggestion_id` היא כלל עסקי ולא אופטימיזציה.** היא מה שמונע
> אישור כפול של אותה הצעה: שני מנהלים שמאשרים במקביל אינם יכולים ליצור שתי מנות שמצביעות
> על אותה הצעה, כי המבנה עצמו לא יאפשר זאת.

### 4.2.4 מרכיב

חומר גלם שהמסעדה מחזיקה. הישות שהמלאי מנוהל עליה.

| שדה | טיפוס | מפתח | חובה | שימוש |
|---|---|---|---|---|
| id | מספר שלם | ראשי | כן | מזהה פנימי |
| name | מחרוזת (100) | ייחודי | כן | שם המרכיב. הייחודיות אינה מבחינה בין אותיות גדולות לקטנות |
| unit | ערך מתוך רשימה | | כן | קילוגרם, ליטר או יחידה. **המערכת אינה ממירה ביניהן** |
| current_stock | עשרוני (10,3) | | כן | הכמות הנוכחית. **אינה יורדת מתחת לאפס** |
| min_stock_threshold | עשרוני (10,3) | | כן | הרף שמתחתיו המרכיב נחשב בחוסר |
| is_active | בוליאני | | כן | מרכיב מושבת אינו מקבל תנועות ואינו נכנס למתכון חדש |
| created_at | חותמת זמן | | כן | מועד היצירה |
| updated_at | חותמת זמן | | כן | מועד השינוי האחרון |

### 4.2.5 שורת מתכון

הקשר בין מנה למרכיב, עם הכמות. **ישות מקשרת עם מפתח ראשי מורכב משני הצדדים.**

| שדה | טיפוס | מפתח | חובה | שימוש |
|---|---|---|---|---|
| dish_id | מספר שלם | ראשי + זר למנה | כן | המנה |
| ingredient_id | מספר שלם | ראשי + זר למרכיב | כן | המרכיב |
| quantity | עשרוני (10,3) | | כן | הכמות הדרושה **למנה אחת** |
| unit | ערך מתוך רשימה | | כן | **חייבת להיות זהה ליחידת המרכיב** |

> **המפתח המורכב אינו רק מזהה, הוא כלל.** הוא מונע מאותו מרכיב להופיע פעמיים באותו מתכון,
> בלי שנדרש כלל נפרד שיאכוף זאת בקוד. זו דוגמה לאכיפה שהמבנה נותן בחינם.

### 4.2.6 שולחן

שולחן פיזי במסעדה.

| שדה | טיפוס | מפתח | חובה | שימוש |
|---|---|---|---|---|
| id | מספר שלם | ראשי | כן | מזהה פנימי |
| table_number | מספר שלם | ייחודי | כן | המספר שהצוות מכיר |
| capacity | מספר שלם | | כן | מספר הסועדים |
| status | ערך מתוך רשימה | | כן | פנוי, תפוס או שמור |

### 4.2.7 הזמנה

מפגש אחד של סועדים בשולחן, מפתיחתו ועד סגירת החשבון.

| שדה | טיפוס | מפתח | חובה | שימוש |
|---|---|---|---|---|
| id | מספר שלם | ראשי | כן | מזהה פנימי |
| table_id | מספר שלם | זר לשולחן | כן | השולחן שעליו נפתחה |
| waiter_id | מספר שלם | זר למשתמש | כן | המלצר שפתח |
| status | ערך מתוך רשימה | | כן | ממתינה, בהכנה, מוכנה, הוגשה, נסגרה |
| created_at | חותמת זמן | | כן | מועד הפתיחה |
| closed_at | חותמת זמן | | לא | מועד הסגירה. ריק כל עוד ההזמנה פתוחה |
| total_amount | עשרוני (10,2) | | לא | **מחושב בסגירה בלבד.** ריק לפניה |

> שלושת המצבים הראשונים **נגזרים** מהפריטים שבהזמנה. שני האחרונים נקבעים במפורש על ידי
> המלצר. `total_amount` ריק בכוונה עד הסגירה, כי לפניה הוא עוד יכול להשתנות.

### 4.2.8 פריט הזמנה

שורה אחת בהזמנה: מנה בכמות מסוימת. **זו הישות שמחזיקה את מרב המצב במערכת.**

| שדה | טיפוס | מפתח | חובה | שימוש |
|---|---|---|---|---|
| id | מספר שלם | ראשי | כן | מזהה פנימי |
| order_id | מספר שלם | זר להזמנה | כן | ההזמנה שאליה שייך |
| dish_id | מספר שלם | זר למנה | כן | המנה שהוזמנה |
| quantity | מספר שלם | | כן | הכמות. **חסומה ב-99** |
| status | ערך מתוך רשימה | | כן | ממתין, בהכנה, מוכן, בוטל, נדחה |
| notes | טקסט חופשי | | לא | הערת המלצר, למשל "בלי בצל" |
| cook_id | מספר שלם | זר למשתמש | לא | הטבח שלקח להכנה. **תיעוד בלבד, אינו נעילה** |
| price_at_add | עשרוני (8,2) | | כן | מחיר המנה **ברגע ההוספה** |
| reject_reason | טקסט חופשי | | לא | הודעת הדחייה. מלא רק במצב "נדחה" |

> **מדוע הכמות חסומה ב-99:** סכום ההזמנה הוא סכום של מכפלות מחיר בכמות, והשדה שמחזיק אותו
> מוגבל בגודלו. תקרה על הכמות מבטיחה שהסכום לעולם לא יחרוג ממה שהשדה יכול להכיל. זו
> הגבלה שנובעת מהמבנה, לא מהעדפה עסקית.

### 4.2.9 תנועת מלאי

רשומה אחת ביומן שמסביר את הכמות של מרכיב. **הטבלה היחידה שהיא בלתי הפיכה לחלוטין.**

| שדה | טיפוס | מפתח | חובה | שימוש |
|---|---|---|---|---|
| id | מספר שלם | ראשי | כן | מזהה פנימי |
| ingredient_id | מספר שלם | זר למרכיב | כן | המרכיב שהושפע |
| movement_type | ערך מתוך רשימה | | כן | קנייה, צריכה, פחת, התאמת ספירה |
| quantity_change | עשרוני (10,3) | | כן | **הדלתא החתומה**, חיובית או שלילית |
| reference_id | מספר שלם | | לא | ההזמנה שגרמה לצריכה. ריק בתנועה ידנית |
| performed_by | מספר שלם | זר למשתמש | כן | מי ביצע |
| timestamp | חותמת זמן | | כן | מתי |
| notes | טקסט חופשי | | לא | הערה חופשית |

> **"צריכה" נוצרת רק אוטומטית**, בעת לקיחת פריט להכנה, ואינה ניתנת לרישום ידני. אחרת אותה
> מנה הייתה יכולה להיות מנוכה פעמיים. הכלל נאכף בשכבת האימות של הבקשה, לפני שהיא מגיעה
> ללוגיקה.
>
> **`quantity_change` נשמר חתום ולא כגודל עם כיוון נפרד.** כך סכום כל התנועות של מרכיב
> אמור לתת בדיוק את הכמות הנוכחית שלו, וזו בדיקת שפיות שאפשר להריץ בכל רגע.

### 4.2.10 הצעת מתכון

תוצר של פנייה לשירות הבינה המלאכותית. **אינה מנה, ואי אפשר להזמין אותה.**

| שדה | טיפוס | מפתח | חובה | שימוש |
|---|---|---|---|---|
| id | מספר שלם | ראשי | כן | מזהה פנימי |
| requested_by | מספר שלם | זר למשתמש | כן | הטבח שביקש |
| prompt_used | טקסט חופשי | | כן | הפנייה המלאה שנשלחה, כולל הכיוון שהטבח הוסיף |
| generated_recipe | מסמך מובנה | | כן | ההצעה: שם, מרכיבים, אופן הגשה |
| ingredients_snapshot | מסמך מובנה | | כן | **צילום המלאי ברגע הבקשה** |
| created_at | חותמת זמן | | כן | מועד ההפקה |
| dismissed | בוליאני | | כן | נדחתה על ידי מנהל |

> **מדוע נשמר צילום המלאי:** בלעדיו אי אפשר להסביר בדיעבד מדוע הוצעה דווקא ההצעה הזו,
> מפני שהמלאי מאז השתנה. זהו תיעוד של הקלט, לא מטמון.
>
> **שימו לב שאין שדה "אושרה".** הצעה אושרה כאשר קיימת מנה שמצביעה עליה, ותו לא. `dismissed`
> הוא השדה היחיד שנשמר, מפני שדחייה אינה משאירה שום עקבה אחרת שאפשר לחשב ממנה.

### 4.2.11 שיחת ייעוץ

הקשר לדיאלוג בין טבח לשירות הבינה המלאכותית, סביב נושא אחד.

| שדה | טיפוס | מפתח | חובה | שימוש |
|---|---|---|---|---|
| id | מספר שלם | ראשי | כן | מזהה פנימי |
| user_id | מספר שלם | זר למשתמש | כן | הטבח שפתח |
| title | מחרוזת (200) | | כן | כותרת לתצוגה, נקבעת בשרת בעת הפתיחה |
| created_at | חותמת זמן | | כן | מועד הפתיחה |
| dish_id | מספר שלם | זר למנה | לא | הנושא, אם הוא מנה בתפריט |

> האימות. זו החלטה מודעת: הכלל הוא עסקי ולא מבני, ואכיפתו בשכבה שמסבירה למשתמש **למה**
> הבקשה נדחתה עדיפה על כשל מבני שמגיע כתקלה כללית.

| שדה | טיפוס | מפתח | חובה | שימוש |

> אינה נשמרת, כדי שלא תישאר בהיסטוריה שאלה תלויה שאיש לא ענה עליה.

## 4.4 כללי שלמות שהמבנה אוכף בעצמו

הטבלה מסכמת אילו כללים עסקיים מוגנים על ידי המבנה עצמו, בלי להסתמך על קוד שיזכור לבדוק
אותם. **ההבדל חשוב: כלל שנאכף במבנה אינו יכול להישבר בגלל נתיב קוד חדש שמישהו הוסיף
ושכח לבדוק.**

| הכלל העסקי | מה אוכף אותו |
|---|---|
| אין שני משתמשים בעלי אותו שם כניסה | אינדקס ייחודי, ללא הבחנת רישיות |
| אין שני מרכיבים בעלי אותו שם | אינדקס ייחודי, ללא הבחנת רישיות |
| אין שני שולחנות בעלי אותו מספר | אילוץ ייחודיות |
| אין שתי קטגוריות בעלות אותו שם | אילוץ ייחודיות |
| מרכיב אינו מופיע פעמיים באותו מתכון | מפתח ראשי מורכב |
| הצעה אינה מאושרת פעמיים | אילוץ ייחודיות על ההפניה מהמנה להצעה |
| כל הפניה מצביעה על רשומה קיימת | מפתחות זרים, יחד עם הכלל שאין מחיקה |
| כמות ומחיר אינם מאבדים דיוק | טיפוס עשרוני מדויק, לא נקודה צפה |

**כל שאר הכללים נאכפים בשכבת הלוגיקה העסקית**, מפני שהם דורשים הקשר שהמבנה אינו מכיר:
כמה מלאי נחוץ לפריט מסוים, האם התפקיד מורשה, האם המעבר בין המצבים חוקי. חלוקת העבודה
הזו מכוונת: **המבנה שומר על מה שנכון תמיד, והלוגיקה על מה שתלוי במצב.**
