## Intro

This checks the draft PRD's claims about entities, fields, and current-state capabilities against the actual code in `backend/data_models/*.py`, `backend/main.py`, and `backend/api/router.py` — not against `docs/*.md`'s summaries of that code (though those summaries were spot-checked and found accurate). Scope: entity/field existence, the four known current-state gaps (CORS, auth, DI wiring, migrations/tests), the FR-16 "suggestion → dish" structural assumption, and the real-time (NFR-1) deferral.

## Gaps Found

- **FR-9 / FR-11 contradict each other on when stock deduction fires.** FR-9's consequence states "Transitioning to `ready` triggers automatic stock deduction (FR-11)" and UJ-2's narrative agrees (deduction happens the moment Amir marks an item "passed"/ready). But FR-11 itself ("Automatic stock deduction on preparation") states "When an Order Item transitions to `in_preparation` (FR-9), the system deducts…" — which also matches the pre-existing `docs/database-schema.md` business-logic note ("When an OrderItem is marked as `in_preparation`, the system deducts…"). Nothing in code enforces either today (no business logic is implemented yet), so this isn't a code conflict, but it is an internal PRD inconsistency that will produce two different NFR-3 atomicity designs and two different UJ-2 sequence diagrams depending on which FR a reader trusts. Needs to be resolved to one transition before `bmad-architecture` consumes this PRD.

- **"Low-Stock Alert" is a Glossary/FR-12 entity with no backing table.** The Glossary (§3) and FR-12 describe it as a first-class notification concept ("one active alert per Ingredient-in-shortage," "an alert clears once…"), but there is no `Alert`/`Notification` table anywhere in the 11-table schema (`user.py`, `menu.py`, `recipe.py`, `order.py`, `inventory.py`, `ai.py` — all read directly). It has to be a derived/computed state from `Ingredient.current_stock` vs `min_stock_threshold` (dedup and threshold-crossing detection are both reconstructable from `StockMovement` history without new fields, so this is *achievable*, just not stated anywhere). Worth flagging explicitly for architecture rather than leaving it implicit — the addendum's UML-crosswalk table lists "Role permissions" as a Glossary concept with no table but misses this one.

- **No schema field traces a published Dish back to the AIRecipeSuggestion it came from.** FR-16's claim ("no code path exists where a Recipe Suggestion writes directly to Dish/Recipe") is structurally true today — `AIRecipeSuggestion` (`backend/data_models/ai.py`) has no FK to `dishes`, so turning a suggestion into a menu item is necessarily a fresh manual Admin entry via FR-19/FR-20, not a conversion mechanism. That's consistent with FR-16 as written. But there's also no provenance field (e.g. a nullable `Dish.source_suggestion_id`) — if audit/traceability from a live Dish back to the suggestion that inspired it is ever wanted (reasonable for a "reduces food waste" success story in the demo), that's an unstated schema change, not just an app-layer decision.

- **CORS/auth/DI-wiring gaps confirmed correctly treated as "build from scratch" — no PRD gap.** Verified directly in `backend/main.py` (no `CORSMiddleware`, no `container.wire()` call) and `backend/api/router.py` (only `GET /health`, no auth dependency). FR-1/FR-2/NFR-2 read as requirements to build, not descriptions of existing behavior, and the addendum explicitly notes `container.wire()` "is not yet activated anywhere in the codebase… and will need to be for any DI-based auth dependency." No contradiction found.

- **Real-time push (NFR-1, FR-6, FR-8) correctly deferred, not assumed trivial — no PRD gap.** No WebSocket/SSE/polling mechanism exists in the codebase today (confirmed — `backend/api/router.py` has only the one synchronous REST endpoint). The addendum's "Deferred Technical-How" section explicitly names WebSockets/SSE/long-polling as open architecture candidates and the PRD itself only commits to "push, not poll, within ~2s" (with the 2s figure itself flagged `[ASSUMPTION]`). Correctly scoped as a technology decision, not asserted as already working.

## Notes (non-blocking)

- All 13 entities the reconciliation was asked to check (`User`, `Role`, `Table`/`RestaurantTable`, `Order`, `OrderItem`, `Dish`, `Category`, `Ingredient`, `RecipeIngredient`, `StockMovement`, `AIRecipeSuggestion`, `AIChatSession`, `AIChatMessage`) exist with field names and semantics matching the PRD's Glossary/FR usage exactly — verified against the model source files, not just `docs/database-schema.md`. No missing/renamed field or enum value found anywhere else (`UserRole`, `TableStatus`, `OrderStatus`, `OrderItemStatus`, `Unit`, `MovementType`, `ChatRole` all match the PRD's usage verbatim).
- `StockMovement.reference_id` is a bare nullable `Integer` with no `ForeignKey("orders.id")` constraint (confirmed in `backend/data_models/inventory.py`) — FR-11's "links back to the Order" is a soft/convention-based reference, not DB-enforced. This matches the pre-existing schema doc's own description, so it's not a PRD error, just worth architecture knowing there's no referential-integrity backstop.
- No PRD-required table/column is missing from the current 11-table model — every FR in scope (FR-1 through FR-21) can be implemented against tables that already exist; the "no migration tool" gap does not block MVP scope as currently written.
